## 端到端链路

1. Feishu 普通 scheduler 触发 `每日公司资讯与分析总结`。
2. 用户任务正文要求公司资讯、分析师摘要和财报日期。
3. function-calling runner 执行行情 / 新闻 / 财报日工具调用。
4. assistant final 没有以逐公司资讯和分析师摘要为主结构，而是转成持仓组合亏损、技术破位和交易动作建议。
5. 最终消息送达用户，用户仍能看到部分财报日期和少量评级信息，但任务交付焦点明显偏离。

## 期望效果

- 该类普通 scheduler 应围绕用户列出的公司逐项输出：最新新闻、分析师评级 / 研报摘要、下一次财报日和必要的不确定性标注。
- 不应自动加入未请求标的，除非明确说明其与用户列出的公司存在直接事件关联。
- 用户未要求持仓复盘或操作建议时，不应把资讯摘要升级为减仓、止损、清仓、加仓等交易动作清单。

## 当前实现效果

- 回复包含部分财报日期和评级线索，但主标题、结论、表格和后半段都围绕持仓盈亏、技术破位和操作触发条件。
- 回复新增 `RKLB`，并写入用户没有要求的持仓股数、成本价、浮盈亏和减仓 / 止损建议。
- 这不是空回复、投递失败或系统不可用；问题集中在普通 scheduler 的任务意图保持和上下文隔离质量。

## 用户影响

- 用户订阅的是公司资讯 / 分析师摘要，却收到接近持仓交易复盘的报告，需要自行筛掉未请求内容。
- 未请求交易动作建议会提高金融自动报告的噪音和误导风险。
- 本次仍包含部分可用信息、消息成功收口且未见错投、数据破坏、敏感信息外泄或全渠道不可用；因此这是质量性问题，不影响主功能链路，定级为 P3。

## 根因判断

- 普通 scheduler 的 answer 阶段可能从同 actor 历史持仓 / 观察池上下文中吸入“组合亏损、成本、动作建议”框架，覆盖了当前任务正文的资讯摘要目标。
- 金融报告 prompt / 后处理对“用户未要求交易建议时不得自动生成动作清单”的约束不足。
- 该问题不同于 heartbeat 执行意图污染：本样本来自普通 Feishu scheduler 的最终 assistant final，不是 heartbeat JSON / noop 协议链路。
- 该问题也不同于异常价格锚缺陷：本样本同时出现高风险行情数字，但本单关注的是任务意图和输出结构漂移。

## 下一步建议

1. 在普通 scheduler answer prompt 中强化当前任务正文优先级，尤其是公司资讯 / 分析师摘要任务不得被历史持仓模板改写。
2. 增加出站或 answer-stage 检查：当用户未请求操作建议时，限制 `动作建议`、`减仓`、`止损`、`清仓` 等交易动作段落。
3. 为 `每日公司资讯与分析总结` 增加回归样本，断言输出覆盖用户列出的公司、分析师摘要和财报日期，且不加入未请求持仓表或交易动作清单。
